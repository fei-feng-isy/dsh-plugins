# AGENTS.md

Guidance for coding agents working on `avantf-mem`.

## Architecture invariants

- **Two stores, one retrieval core.** `memory` and `knowledge` are separate, self-contained stores (own DB + own read model). Both build on `retrieval-core` (`@avantf/mem-core`).
- **Cross-retrieval = joint fusion.** Memory and knowledge are queried separately, then candidates are merged and `min-max`-normalized over the *merged* pool so scores are comparable. Never normalize per-store. This describes the CROSS-store step only: inside a store each leg is scaled by its own maximum (`retrieval-core/src/fusion.ts`), which is not a `min-max`, so do not read the `min-max` above as describing in-store fusion. (One leg, the HRR probe, can be capped in a non-score order and is therefore not cap-invariant — see DESIGN §20.17.)
- **Retrieval pluggability is internal.** `SemanticBackend` / `Reranker` / `VectorStore` are swap-enabled through a registry + config inside `retrieval-core`. The business flow (stores, tools, UI) depends only on the interfaces. **Do not** register them as DSH plugins or Cordis services; do not let the DSH plugin select a backend.
- **One dispatch table, one retrieval orchestration.** The contract-tool-key → runtime mapping lives ONLY in `core/src/dispatch.ts`, shared by the DSH plugin (tools + Remote gateway) and the MCP server; the retrieval flow both stores run (limit → weights → over-fetch → leg cap → fuse → live filter → rerank → slice → output budget → health event) lives ONLY in `core/src/store/hybrid.ts`. Both were duplicated once and both copies drifted: the MCP server advertised four `kb_*` tools its own switch had never heard of (every call answered `unknown tool key`), and the `NaN` limit guard / `over_fetch_factor` / `recordLegCapped` each existed on the memory side only. Do not re-fork either — a new tool key goes in the contract and in `dispatch.ts`, a new leg goes in a store's `searchLegs`.
- **Generate is external (Plan A).** The plugin returns retrieved context + provenance only. It never generates answers inside the plugin.
- **Memory has no user isolation** — a single shared store (agent context). Keep `user_hash` partitioning out.

## Conventions

- TypeScript, `module: NodeNext`. Relative imports use a `.js` extension.
- Single source of truth for tool/config schemas is `@avantf/mem-contract` (`zod`). Every tool schema, MCP inputSchema, CLI arg, and UI payload type derives from it.
- **Dependency versions live in `pnpm-workspace.yaml`'s `catalog:`**, referenced as `"catalog:"`. Bump the catalog line, never a `package.json`. `zod` is pinned exactly there because `@avantf/mem-contract` and `@avantf/dsh-mem` must load the SAME copy: two copies — even of the same major — have incompatible type identities, which is what forced the `TypertSchema['schema']` cast (DESIGN §20.11). `pnpm why zod` must keep resolving ONE copy for `@avantf/mem-contract` and `@avantf/dsh-mem` — it
  also lists a transitive copy under `@modelcontextprotocol/sdk`, which is not ours: the MCP server
  hands that SDK plain JSON Schema, never a schema object, so no zod identity crosses the boundary.
- **The `@avantf/*` family dependency is provisioned, not bundled.** `@avantf/dsh-plugin-base` — ONE package carrying the family's environment-initialisation framework, its host compatibility gate (rules / probes / verdict / report / post-registration verification), and the shared kit (`src/kit/**`) — is a **peerDependency** of the plugin (peer range `^0.1.0`; the plugin also declares `^0.1.3` in `devDependencies` so `pnpm install` installs it) and must **never be bundled** and **never imported by specifier**: the plugin's only static reference is a zero-dependency bootstrap inlined into the bundle (`packages/plugin/src/envinit-bootstrap.js`, vendored from the installed base's `dist/bootstrap.js`), which resolves base by `createRequire(...).resolve('@avantf/dsh-plugin-base/package.json')`, dynamically `import()`s it, and validates the version against the inlined `supportedRange`. The engine (`@avantf/mem*`) stays in `devDependencies` so tsdown inlines it. The old `@avantf/dsh-envinit` and `@avantf/dsh-compat` packages are **dead**: no new versions, nothing depends on them. Local development needs no checkout: `scripts/link-envinit.mjs` (run by `pnpm build:dsh`) reads the installed base and vendors its zero-dependency `dist/bootstrap.js`/`dist/bootstrap.d.ts` into `packages/plugin/src/envinit-bootstrap.{js,d.ts}` (`DSH_ENVINIT=<checkout>` is the explicit opt-in that symlinks a checkout and vendors from it instead); the host half is bundled by tsdown from tsc output, so `scripts/copy-envinit-bootstrap.mjs` moves the vendored bootstrap into `lib/types/` **between `tsc` and `tsdown`** and `scripts/assert-envinit-artifacts.mjs` asserts afterwards that the bootstrap is inlined, the base is never imported by specifier, and `lib/client.js` is clean (`scripts/pack-plugin.mjs` re-asserts the same on the packed tarball). **Publish the base BEFORE the plugin**: the publish gate (`scripts/release-check.mjs`) refuses to publish a plugin unless the registry already carries a `@avantf/dsh-plugin-base` version inside the plugin's accepted peer range. Tarballs must never carry `link:`/`file:` specifiers (`scripts/pack-plugin.mjs` and `make-release-tree.mjs` both refuse one). `zod` resolves to ONE copy for the whole merged workspace from the ROOT `pnpm-workspace.yaml` `catalog:` (`zod: 4.6.5`, tracking the version the installed dsh ships) — bump the catalog line, never a `package.json`; the base's `zod` peer stays the wide `>=4.4.3 <5` so the same base serves both the workspace and the installed dsh. Shared business logic is consumed at RUNTIME from base, so a fix there ships with ONE base release and no plugin rebuild — the one exception is the `typert` `strict` wire codec and the small literal descriptor conventions, which stay in each plugin (they mirror a host convention in a couple of lines); changing those needs a plugin release. **The family's three hard constraints** (invariants): (1) envinit-style provision must **never be bundled and never statically imported** by a plugin; (2) base is **provided by the framework/host and loaded dynamically by file URL**; (3) **publish order is base → plugins**, and tarballs carry no `link:`/`file:`. **Judgement rule for "runtime-base or plugin-local?"**: ask *"must this knowledge be fixable by ONE base release?"* If yes → consume it from base at runtime. If no (it is only a two-or-three-line literal mirroring a host convention) → it may stay in the plugin, but then say **"changing it needs a plugin release"**. After changing shared code under `base/**`, re-run BOTH plugins' complete gates: mem `pnpm build:dsh` + `node scripts/mount-smoke.mjs`, work `pnpm release:check` + mount-smoke.
- **The plugin's `@deepseek-ai/*` must be the same copy as the running `dsh`.** `scripts/link-dsh.mjs` links them from the INSTALLED global dsh (`npm root -g`) and from nowhere else; linking one copy and running another gives the plugin a different harness than its host, and `ctx.typert.register`/tool registries are keyed by object identity. The plugin's **compile, type-check and mount target ONLY the installed dsh** — there is no checkout mode, and no mode flag. tsdown's client preset is the verbatim copy **pinned in this repository** under `packages/plugin/vendor/dsh-client-preset/` (8 files / 2334 lines, origin and re-alignment steps in its `ORIGIN.md`), imported by a literal relative specifier and never selected by an environment variable, so a build needs no harness source at all. That copy defines the browser half's ABI, so it is copied verbatim and must stay byte-identical to the pinned harness revision. A harness checkout is used **only** by the optional drift cross-check `scripts/check-preset-drift.mjs` (also printed as a `link-dsh` WARNING / `release-check` note when a checkout is present) — it never takes part in compiling, type-checking or mounting. Do not trim or "simplify" the copy; when it must move, re-copy verbatim, update `ORIGIN.md`, and re-verify that a harness-preset build and a vendored-preset build produce the same `lib/index.js` + `lib/client.js` sha256.
- Reading zod internals: use `def.type` / `def.shape` (an object) / `def.values`, and prefer `z.toJSONSchema(schema, { io: 'input' })` over hand-rolled derivation. A wrong internal read is SILENT — fields flatten to `{}` with no type error — so the pinned shape assertions in `contract.spec.ts` / `tool_schema.spec.ts` are the gate, not optional coverage. Do not use `.default({})` on a nested schema: v4 does not parse the default through it — use `.prefault({})`.
- Config layering: built-in defaults → `.avantf/configs/common.yaml` → store config → environment → explicit. Do not add a new precedence level unless the design requires it.
- Add tests for every domain unit. The retrieval parity gate is the Chinese eval set (`packages/core/src/eval` + `packages/core/test/eval_zh.spec.ts`, 35 queries — it began as 29 and was extended with the two-CJK-character shape); its summary numbers are FROZEN and asserted bit-exact, so a change that moves retrieval has to re-freeze them with the movement explained. It lives in `@avantf/mem`, not in `@avantf/mem-contract`: the eval drives the stores, and the contract has no runtime to drive.
- `pnpm typecheck` also checks `test/` (each package's `tsconfig.test.json`): keep test-only types
  honest — a spec that references a missing type or a shape the runtime never returns is a bug the
  transpiler will not report. CI runs this **after** `pnpm build` (a package reads its dependencies
  through their emitted `lib/*.d.ts`).
- `pnpm typecheck:dsh` covers `packages/plugin` (src + specs). It is a **local** gate: it resolves
  `@deepseek-ai/*` through the installed DSH harness, which CI does not have, so run it by hand
  before touching the plugin. It is separate from `pnpm typecheck` for exactly that reason, not
  because the plugin is exempt from the rule.

## Directory structure

Do not move data files outside `~/.avantf/{memory,knowledge}`; everything a user EDITS lives in
`~/.avantf/configs/*.yaml` and `~/.avantf/prompts/*.md`, never next to the databases. Keep the `retrieval-core` boundary: adapters in `retrieval-core`, stores in `core`, the DSH plugin in `plugin` is a thin shell (no backend selection).
