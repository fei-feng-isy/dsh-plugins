# 改进项对 mem 插件的落地影响分析（基线 mem 0.5.0）

> **范围**：四份文档里提出的全部改进 —— 方案 `RETRIEVAL_GENERALITY_PLAN.md`（L1–L4）、补遗
> `RETRIEVAL_HIT_RATE_ADDENDUM.md`（E0/F1–F4）、审查 `RETRIEVAL_GENERALITY_PLAN_REVIEW.md`（R1–R9）、
> 对照 `HINDSIGHT_COMPARISON.md`（A1–A16 / B1–B5）—— 逐项分析**对记忆插件本体**的影响。
> **基线**：当前 HEAD（mem **0.5.0**，2026-10-05；schema v9；`WIRE_VERSION=2`）。
> **方法**：只读代码与门禁配置；本文只写文档，不改任何代码。

---

## 0. 结论速览

1. **真正"伤筋动骨"的只有四类**：**改排序/改分**（移动 41 条冻结数字）、**加列加表**（单向迁移，DB 一旦升级
   旧 build 拒绝启动）、**改契约/信封**（wire 版本、两半 skew）、**改共享抽取器**（memory 与 knowledge 一起动，
   而 kb 没有评测网）。
2. **多数改进是加法**（新字段/新开关/新参数、默认行为不变）⇒ 单项风险低，但每一项都要付一笔**固定税**：
   一条迁移、或一次 wire bump、或一次"重冻并解释"。
3. **文档已落后于 HEAD 一处，必须先重基线**：0.5.0 已**整体移除重排能力**（`0450c3e feat(mem)!`：删配置键与
   统计字段、删 `retrieval-core/src/rerank.ts` 与本地重排适配器、`WIRE_VERSION 1→2`、健康面板不再显示重排）。
   因此 **补遗 F3(a)/F3(b)、审查 §9 的"修 `rerank_used` 假计数"、对照 §2.6/§5 的"若重开重排"全部过时**——
   现在"重开"是**重新引入一个已移除的能力**（重开条件写在 `DESIGN.md` §5.1）。
4. **建议顺序**：先做**零运行时影响**的三件（E0/A12 评测纪律、A6 信封、A1/A11 守卫与文案），再按批次动排序
   （A6 是验收前提），最后才动结构（A2/A3/A9/A10/B1）。

## 2. 影响维度 × 门禁矩阵

| 维度 | 什么会触发 | 触发的门禁/产物 |
|---|---|---|
| 数据与迁移 | 新列/新表/新枚举 | 迁移编号 +1、`db_upgrade_parity` 全覆盖、旧版本回滚需备份、`memory.ts` 读写面 |
| 排序与数字 | 新腿、改融合、改腿的分数、boosts、门槛、被索引文本 | 41 条**重冻 + 解释**、真实库对照、E0 不退化、变异验证 |
| 契约与 wire | 新工具参数、信封新字段、载荷形状变化 | `WIRE_VERSION` +1、两个 wire spec、client 渲染、MCP/CLI 派生、形状断言 |
| 用户可见行为 | 拒绝写入、默认返回集变化、提示词/文案 | CHANGELOG `[0.6.0]`、README 计数、面板文案 |
| 知识库联动 | 改 `extract.ts` / `hybrid.ts` / 信封 | kb 回归（**当前无 kb 评测**）⇒ 至少补一次性对照脚本 |
| 性能 | 新腿、图遍历、时间解析 | 每次检索的 SQL/候选预算（`legCap`/`overFetch`）；**hint 路径必须保持同步**（不能 await 模型） |
| 部署面 | 新依赖、新模型、新数据文件 | 零运行期依赖红线；预装/下载策略；离线可用 |

## 4. 叠加效应与批次（哪些必须一起做、哪些必须错开）

1. **一切"动分"的项共享同一笔重冻税**：A2/A4/A5/F4/F1/L1/L3/L2/A10 ⇒ **必须串行成批**，每批一次重冻 + E0 回归，
   否则无法归因（这也是对照 §5 说"先 F4 再 L3"的理由）。
2. **A6 必须先行**：没有逐臂/融合后分数，A5（boost）、A7（弃答）、A2/A10（新腿）都只能"看结果猜原因"，
   L2 重写也没有落点。它自己是**纯加法**（只加字段 + 一次 wire bump）。
3. **迁移项应尽量合并成一次编号迁移**：A2 + A9 + A10 + A13（+ B1/B2/B3 的列）如果分开发，会连续抬高
   **单向迁移墙**（每次升级后回滚都要备份）。合并到一个发版窗口最省用户成本。
4. **A3 与 A4 是同一处管道的两个消费者**：实体袋变了要同时刷新"被索引文本"（A4）与 HRR——**同批做，
   升一次 `ENTITY_EXTRACTOR_VERSION`**，否则会出现两个 vintage。
5. **A1 与 A11 是唯一与排序完全解耦的项**；A1 是**用户可见行为**（拒绝写入）⇒ 需要 `[0.6.0]` 条目与文档。
   **A1 已按复核提到批次 0/1**（数据根带 git 远端、成本最低、不移动冻结数字；`HINDSIGHT_ANALYSIS_REVIEW.md` §3.1），
   并新增一条**用户侧**项：`.gitignore` 掉 `memory.db-wal`/`-shm` + 提交前 `wal_checkpoint(TRUNCATE)`（§3.2）。
6. **F3 类项全部作废**（重排已移除）；对照文档里"重开重排"的讨论只在 `DESIGN.md` §5.1 的重开条件被满足时才有意义。
7. **kb 半边**：A3/A4/A6（以及任何改 `hybrid.ts`/`extract.ts` 的项）都会经过 kb；kb **没有评测**，
   所以每批必须附一张一次性 kb 对照（≥10 条 kb 查询的前后 id/顺序）。

## 5. 红线（任何改进都不能碰）

- **引擎零 LLM**（写读都不调用生成式模型）；**离线可用**；数据不出 `~/.avantf`。
- **零运行期依赖**、`zod` 只做 required peer、源码不静态 import base、可发布集合恰好三个包。
- **工具面 8 个**（不含 `kb_manage`）；契约是唯一真源。
- **迁移单向**：不得用"删列/改语义"来省事；回滚必须靠备份。
- **冻结数字纪律**：移动就要重冻并解释，且要有 E0 级不退化证据；**hint 路径保持同步纯字符串**。
- **数据路径**：用户编辑物只在 `configs/*.yaml` 与 `prompts/*.md`；知识库 managed `.md` 是源，派生内容不得覆盖它。

## 6. 风险最高的三项（建议先做可逆验证）

1. **L1/B1（写侧结构化）**：价值最高、迁移最重、且**查询侧语义未定**（过滤=收窄 vs 新腿）。先做
   "写侧参数 + 只读探针"的 spike，不动 schema：用现有 `category`/实体表模拟一次精度对照。
2. **A2（时间）**：中文规则工作量大且会动门槛；先用**纯离线脚本**在真实库上验证"时间窗查询"的召回合不合理，
   再决定它是一条腿还是一个 boost。
3. **A3（实体规范化）**：会同时改两 store 与 HRR 的输入，且必须升版本重扫；先做"合并前后实体袋规模 + 目标查询
   前后对照"，再落库。

## 9. 一句话结论

这些改进对 mem 的**主要成本不是代码量，而是三笔固定税**——**单向迁移**、**wire 版本**、**冻结数字重冻**；
其中价值最高、且能立即降低后续风险的是 **A6（信封）+ E0/A12（评测）** 这两条"零行为变化"的前置；
风险最高的是 **L1/B1、A2、A3** 三处结构性改动，都应先做**不动 schema 的可逆验证**再落库。
