## 1. 现象

同一份记忆、同一个引擎，只换问法，结果就翻车：

| 查询（产品级 `search`，融合分） | top-1 | 分数 | 是否靠**放宽档**兜住 |
|---|---|---:|---|
| `我是谁？` | **#4** ✅ | 0.550 | **是**（`relaxed=true`）——严格档被 0.5 门槛挡掉 |
| `用户是谁` | **#4** ✅ | 0.700 | 否（严格档直接命中） |
| `用户的信息` | **#4** ✅ | 0.700 | 否 |
| `我的名字` | #4 ✅ | 0.700 | 否 |
| `我的名字是什么` | #4 ✅ | 0.450 | 否（命中但分低） |
| **`我叫什么`** | **#95** ❌ | 0.550 | 否（**命中错误事实**） |
| **`我是做什么的`** | **#95** ❌ | 0.550 | 是（放宽档也没救回来） |
| `插件的安装方法`（对照，无关） | #122 | 0.550 | 否 |

两条要点：① 「我是谁？」**靠放宽档才勉强命中**；② 换一种自指说法（`我叫什么`）**直接命中错误事实**。
③ 对照查询（无关）也拿到 0.550 —— 说明**这个 `score` 是融合后的相对分，不能跨查询当绝对关联度看**（见 §2）。

## 2. 现状机制（决定"能不能修、往哪修"）

- **门槛**：严格档语义 `min_semantic_similarity = 0.50`（默认）；实体腿 `min_jaccard`；FTS 腿按"命中的查询词元数"，
  且已做**可达性钳制**（3 字中文查询只能产出 1 个 trigram，配置的 2 对它不可达）。
- **自动放宽档**（`LOOSE_FLOORS`：语义 **0.40** / Jaccard 0.15 / FTS 为"查询词元数的一半、下限 1"）**只在**
  "严格档返回空 **且** 确有候选被门槛丢掉（`dropped_by_floor > 0`）时触发一次。
- **分数是相对的**：`retrieval-core/src/fusion.ts` 按**每条腿自身的最大值**归一，所以融合分只在**同一次查询内**可比；
  门槛之所以钉在**腿上的原始分**（cosine / Jaccard / 命中词元数），正是因为原始分才有绝对尺度。
- **模型**：`bge-base-zh-v1.5`（768 维；**2026-10-04 起的 shipped 默认**；§3.1 对比表里 small 是原默认），
  **查询与文档同一种编码、没有用 BGE 官方要求的检索指令前缀**——前缀已**实测否决**（§4-D）；
  重排是 `rerank=none`（`bge_reranker` 已注册、可用但未启用）。
- **条件提示（hint）**：`relevance(text)` 是**同步**判定（`plugin/src/index.ts:739`），判据是"查询词面在 FTS 表里
  **命中 ≥2 个不同词元**"（`store/lexical.ts:75`，逐词元 `LIMIT 1`，`stopAt=2` 提前收）。**第一人称问句对第三人称事实
  词面零重叠 ⇒ 这类查询在 A② 之前必然不触发 hint**（这是自指问句的第二处失联，见 §4-A②；**A② 已实施**：改写文本的
  词元也算一遍，`我叫什么` 对 `用户的名字是…` 由 0 命中变为 3 命中，见 §0 记录）。
- **仓库既有实测**（`mem/packages/core/src/store/floors.ts` 的注释）：自指问句对正确事实的**原始余弦 0.444**，
  四个无关查询的上限 **0.384** —— 余量只有 **0.06**。这条注释同时论证了为什么**不能**用"豁免 `pinned` 事实"来救
  （豁免只让事实进候选池、不加分；小库上会退化成"每次查询都带全部 pinned"），本方案沿用这个结论（§5 不做）。

### 3.2 从实测读出的三条成因

1. **视角不匹配 + 词法零重叠**：事实是从**第三人称/用户视角**写的（"用户…"），问句是第一人称 →
   语义腿要独自承担判别，而 FTS/实体腿贡献 0。改写后**同一模型**下分数 +0.15~0.24（`用户是谁` vs `我是谁？`
   = **+0.21 / +0.22 / +0.21**；`用户是做什么的` vs `我是做什么的` = **+0.24 / +0.18 / +0.16**），
   并且**改写是三条路径里唯一能让这一族越过 0.5 的**（0.685 / 0.677 / 0.626）。
2. **短身份事实在稠密相似度下天生弱**：正确事实只有 **9 个字符**（mean-pooling 的短文本向量信息量低），
   而 396 字符的无关事实对**任何**查询都有 **0.428–0.485** 的"基础相似度" → 不是"模型不够大"，
   而是**短事实 vs 长文本**这一组合本身不适合靠 cosine 判别。这解释了"问法一变就翻车"。
3. **语义腿可能未就绪、且没有第二道打分**：模型是异步加载的，首次查询可能只剩词法腿（冷启假阴性）；
   `rerank=none` 时没有 cross-encoder 兜底。

**关于换模型的结论（实测）**：base/large 能修**排序**（`我叫什么` 从 −0.064 的劣势翻到 +0.10 / +0.12），
但**修不了绝对分**（`我是谁？` 三个模型都 < 0.5：0.476 / 0.459 / 0.420），而且 large 对正确事实的分数
**反而更低**；代价是 16.6 s / 35.4 s 冷启与 389 MB / 1.3 GB 体积，外加**门槛与冻结数字整体平移**。
所以：**换模型不是这个个案的第一手段。**

### 3.3 两条针对评审的补充实测

- **既有 `triples` 能不能替 C 做结构化过滤：不能（今天）**。实测 `fact_id = 4` 的三元组 **0 条**，
  且全库 `pred` 分布噪声大（`没有:12 / 发布:9 / 默认:8 / 提示:7 …`）——抽取器的谓词还没干净到能当过滤键。
  结论：C 若要做，仍需**槽位**（或先改抽取器质量），不能"复用现成的"。
- **hint 的判据与同步性**（支撑 §4-A②）：`store/lexical.ts:75` 的"两个不同词元"是**经测量定下的**门槛，
  `relevance()` 在**入站文本上同步**调用（`plugin/src/index.ts:739`）——所以纯字符串改写表与它天然兼容，
  而"等模型热再判定"则不行。

### A 的实现细节（评审要求写死）

- **增广，不是替换**：**原查询与改写查询各自走一遍检索**，候选取**并集**，各腿按各自**原始分**照常计入融合
  （不做"改写分数叠加"之类的加权）。理由：意图表是**封闭集**，中文自指变体极多（"我叫啥" / "本人是" / "我是干啥的"），
  误判不可避免；**增广式下误判的代价只是"多召回一点"，替换式下则是"改变了用户真正问的东西"**。
  这与自动放宽档"**只放宽、不收窄**"的既有纪律同构。
- **一次改写只产出一个规范形式**（不做无界扩展）：保证成本上界与融合可比性；扩展再多是 B/C 的事。
- **不改写非自指查询**：识别为自指的才加一路；其余查询路径与今天**逐字节一致**（可测）。
- **A②（hint）建议一期就接**：hint 的语义正是"让模型知道有相关记忆"，自指问句恰恰是该响的场景；共用同一张表，
  成本近零，且它是**同步纯字符串**判定，与"等模型热"无冲突。若一期不接，文档要写明是**刻意留到二期**而不是遗漏。

## 5. 推荐与分期

**第 1 期（不改门槛、不换模型）**：`H`（哨兵，含自身重冻）→ `A`（增广式改写）→ `A②`（hint 复用同一张表）→ `G`（仅词法标注）。
预期：`我是谁？` 从"靠放宽档兜住"变成"**严格档命中**"，`我叫什么` / `我是做什么的` 不再翻到错误事实，**0.5 门槛保留不动**。

**第 1 期之后先做一次增量重测（这是进入第 2 期的门）**：用 §1 那张表 + §6 哨兵复测。
**若 A 单独已让全部哨兵过严格档 ⇒ B/C 降为第 2 期候选**（B 的"把身份事实统一写成用户…"这一形态对 #4 是**空操作**——
它本来就是"用户…"写的，这正是第三人称改写有效的原因；失败方向在**查询侧**）。

**第 2 期（需重新校准）**：`D` 已在 2026-10-04 **实测否决**（§4-D：每条查询都变差，余量 +0.307 → −0.358），
**从候选中移除**。第 2 期只剩 **`E`（启用 reranker）** 与 **换更大模型**：`bge-base-zh-v1.5` 已于 2026-10-04
成为 shipped 默认（§3.4 复评：0.5 不动）；**不推荐 `bge-large`**（+0.12 余量换来 35.4 s 冷启、1.3 GB、绝对分下降）。

**明确不做**：
- **不豁免 `pinned` 事实**（仓库已论证：只进候选池、不加分，小库上退化成"每次查询都带全部 pinned"，还会污染本该为空的弱查询）；
- **不调低全局默认门槛**（拿整库精度换个案）；
- **不把融合分当绝对关联度**（它是按腿最大值归一的相对分）；
- **不在查询前等模型热**（预热被三段门刻意推到首屏之后；首查阻塞等 ONNX 等于把 §20.14 修掉的问题请回来）——
  冷启只做**标注**（G）。

## 6. 验收判据（实施前先落地）

1. **冻结 eval 增补自指问句**，断言 **top-1 = 正确事实** 且 **`relaxed` 不为真**（"必须来自严格档"比分数阈值稳定得多）：
   - **4 条表内**（`我是谁？` / `我叫什么` / `我的名字` / `我是做什么的`）；
   - **再加 1–2 条表外变体**（如"我叫啥""本人是谁"）并**钉成已知缺口**——否则 4 条恰好全被意图表覆盖，
     测试会绿得空洞（本仓 "PINNED GAP"（2 字动词）先例同款处理：**让覆盖边界可见**，而不是被表悄悄修没）。
   - **第 1 期实施后（2026-10-04）**：A 的意图表把这两条也覆盖了（`我叫啥`→`用户的名字`、`本人是谁`→`用户是谁`），
     所以它们**改成与表内相同的断言**，"让覆盖边界可见"改由**常驻的关表变异块**承担：把意图表关掉
     （`rewriteQuery: () => undefined`）时这 6 条必须回到 §3.1 的修前行为。同一块还证明哨兵**不是空洞的**
     （关表后至少一条不再满足严格档哨兵），而不是"恰好全被表覆盖、测试恒绿"（§0 记录）。
2. **fixture 必须复刻病理结构**：**9 字符短事实 + 396 字符、对任何查询都有 0.43–0.49 基础相似度的干扰项**。
   合成语料若没有这种**短/长不对称**，哨兵在健康语料上可能天然全绿、守不住真东西（§20.17"空洞断言"同款教训）。
3. **真实库回归表**：修前/修后逐条对比（用 §1 与 §3.1 两张表做基线）——与 1、2 两层**缺一不可**。
   **（第 1 期未做：本轮只跑确定性 fixture；本机活库的修前/修后逐条对比留待第 1 期后的增量重测，见 §0 与 §5。）**
4. **不得回归**：对照的无关问题仍然**空或低分**（增广不能把无关问题也拉进来）。**（已做部分：非自指查询走
   `undefined` 分支、与改动前逐字节一致，由 `self_query.spec.ts` 用冻结集里的非自指查询钉住；"无关查询仍空"
   的产品级对照留待同一轮增量重测。）**
5. **H 自己会动冻结数字**：往冻结集加查询本身就移动汇总指标，故 **H 落地那一步就要重冻一次并解释**
   （仓库规矩："任何移动它的改动都要重新冻结并解释"）；不是等到第 2 期。
6. 若走第 2 期：门槛重新校准 + `eval_zh` 冻结数字复核 + 模型体积/冷启记录更新。
