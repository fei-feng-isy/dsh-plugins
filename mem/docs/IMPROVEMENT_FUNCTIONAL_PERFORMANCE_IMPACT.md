# 改进项对 mem 的**功能**与**性能**影响分析（基线 mem 0.5.0）

> **与 `IMPROVEMENT_IMPACT_ANALYSIS.md` 的分工**：那份讲"改动面与固定税"（迁移 / wire / 重冻）；
> 本文讲**功能后果**（能力增量、行为变化、回归风险）与**性能账单**（每次读、每次写、常驻与启动）。
> **性能基线**取自 `docs/PERFORMANCE_REVIEW.md` 的实测表（该表是评审时的读数，其中若干项已被后续修复改善，
> 例如非语义腿的 `LIMIT cap`、hnswlib 的 tombstone 驱逐；引用时注明，**增量必须在选定规模上重测**）。
> 改进项编号沿用 `HINDSIGHT_COMPARISON.md`（A 系列）与 `RETRIEVAL_GENERALITY_PLAN.md`/补遗（L/F 系列）。

## 0. 结论速览

**功能**：真正的**能力增量只有四处**——① 时间语义（A2）、② 写侧结构化→按主体取一组（B1/L1）、
③ 信念层与自维护派生页（B2/B3）、④ 逐臂可解释与显式弃答（A6/A7）。其余是行为微调或纯内部。
**两处功能回退风险**：L2（若保留，单腿强命中会被删）、A1（误伤会拒掉合法记忆）。

**性能**：
- **两处数量级风险**：**L3**（长事实分块 ⇒ 嵌入成本 ×(1+K)、向量数 ×K、启动/常驻/索引随之 ×K）、
  **F1**（放宽档触发面从"严格档空"扩到"命中数 < k" ⇒ 大量查询要跑**第二遍完整腿集**）。
- **两处可能反而变快**：**A3**（实体规范化把实体袋变小 ⇒ 候选扇出与 Jaccard 成本下降）、**A15**（少解码文本）。
- 其余多数是"每次调用 µs–ms 级"：A1/A5/A7/A9/A11/A13/A14 几乎免费；A6 无 CPU 代价，
  **默认关（`include_scores` false）⇒ 默认不增加模型上下文 token**，显式打开时才付（见 §3.1）；
  A2/A4/A10/F1 是真实增量，需按"腿的 SQL 成本 + 触发率"来量。
- **最需要先建的性能基线不是 p50，而是三条轴**：**每次检索的 SQL 次数与每腿匹配行数（扇出）**、
  **每次写入的分项成本**、**RSS / db / FTS 索引字节**。所有新腿都叠在第一条轴上。

## 1. 当前性能画像（实测基线）

### 1.1 读路径（记忆侧，stub 语义以隔离 ONNX；`PERFORMANCE_REVIEW.md` §3.1）

| 操作 p50 | N=2k | N=10k | N=33k |
|---|---:|---:|---:|
| `recall search`（选择性） | 18.4 ms | 74.4 ms | 234.5 ms |
| `recall search`（常见词，全库命中） | 18.3 ms | 94.4 ms | 314.6 ms |
| `recall search`（零命中） | 0.35 ms | 0.21 ms | 0.36 ms |
| `recall probe`（含 HRR 腿） | 91.1 ms | 451.9 ms | **1366.4 ms** |
| `kb_query`（跨库） | 14.8 ms | 79.2 ms | 262.2 ms |

**结构**：一次 `search` = 每 store 的腿数 ×（1 + 增广改写遍数）+ `fuse` 全池排序 + 取文本。
memory 有 **4 腿**（语义 / FTS / 锚点实体 / HRR），knowledge 有 **3 腿**；跨库 = 两者之和 + 合并。

**两条成本轴（决定所有新腿的代价）**：
1. **腿的 SQL 成本 ∝ 匹配行数**，`LIMIT cap` 只减少*返回*、不减少*扫描与打分*（`store/memory.ts` 的
   `ftsPath` 注释：FTS5 仍为每个匹配打分后再 LIMIT）。⇒ 常见词查询在天花板上是"全库打分"。
2. **fusion 成本受 `legCap` 约束**：默认 `max(200, overFetch×4)`（`over_fetch_factor=5`，limit=10 ⇒ **200/腿/遍**）。
   ⇒ 每新增一条腿 = 每遍 +≤200 个候选进池 + 一次 SQL；增广时 ×2。

### 1.2 写路径与后台（§3.1/§3.2/§3.3）

| 项 | 读数 |
|---|---|
| `remember add` | 6.0 ms@2k → 43.2 ms@33k（不含真模型嵌入） |
| `remember update` | 9.7 ms@2k → 44.5 ms@33k；**有向量后端时 664 ms@8k → 13872 ms@16k**（ANN 重建路径） |
| 真模型 `kb ingest` | **37.4 ms/chunk**@299 → **33.7 ms/chunk**@4499（单块 ~300 字符 encode **39.3 ms**） |
| 查询 encode（短） | ~4 ms（`hybrid.ts` 注释：放宽档重试重编码 ~4 ms） |
| 启动 `buildRuntime` | 763 ms@2k → **6285 ms@8k** → **14688 ms@16k**（含建索引） |
| kb 启动（重开含向量） | 5.6 ms@299 chunks → **1635.6 ms**@4499 chunks |
| `trustTick`（预算 5000） | 80.0 → 356.2 ms |
| `maintenance`（settleAll） | 27.3 → **1322.5 ms**@33k |
| 微基准 | `estimateTokens` ~30 ns/字符；`fitToTokenBudget` 11–12 ms/500 条；`track=true` 每次 search 写 WAL **8.6 KB**（+0.4 ms） |

### 1.3 常驻与磁盘（§3.1/§3.2/§3.3）

| 指标 | N=2k | N=10k/8k | N=33k/16k |
|---|---:|---:|---:|
| RSS（含 ONNX 模型） | 398 MB | 525–629 MB | 775–893 MB |
| `memory.db` | 19.1 MB | 94.4–104 MB | 312.5 MB |

**注意**：RSS 的绝对量里含 ONNX 常驻；判断改进的增量要看**向量条数 × 维度 × 4B** 与**FTS/边表字节**，
而不是看整机 RSS。

## 2. 功能影响

### 2.1 能力增量（真正新增的、用户/模型能感知的）

| 项 | 新增能力 | 行为变化 | 回归风险 |
|---|---|---|---|
| **A2 时间语义** | 能回答"上个月/今年/上周做了什么" | 时间窗查询优先返回窗口内事实（新腿 + 可选 boost）；窗口外事实仍由其它腿返回（只作一腿，不做过滤器） | 时间表达误判会把整次查询的排序带偏（对照 hindsight 的 dateparser 误判教训）；中文规则必须**只作一腿**才不致退化成过滤器 |
| **B1/L1 主体·属性** | "我是谁？"能取回**一组**身份事实（职业/公司/家人），而不只是 top-k | 查询可能返回"一个主体的一组事实"而不是按分排序的 k 条 | 若做成**过滤**（收窄）：违反"并集不收窄"，会丢单腿强命中；若关键词式判主体：泛词（`用户` df=14/84）会把干扰项收进组 |
| **B2/B3 信念与派生页** | 得到"已合并的信念"与"常驻答案页"（读时无需检索） | 同一问题可能返回**一条信念**而非多条事实 | 必须带 `source ids`，否则证据不可回溯；派生页与知识库"路径即真相"的边界要写清（派生页不是源） |
| **A6 逐臂可解释** | 模型/面板能看到"这条靠哪条腿、几分"；**按调用可选（`include_scores` 默认 false）** | 默认**零变化**；显式打开时结果 JSON 每 hit 多 4 个字段 | 无功能回退；默认关 ⇒ 不给日常工具调用加 token 税（见 §3.1） |
| **A7 显式弃答** | 低置信时能返回"没找到"而不是最不烂的一条 | 默认关；显式传 `min_final` 时生效 | 默认行为不变（守住"无门槛 top-k"以外的语义） |
| **A1 写侧密钥守卫** | 防止明文密钥进入持久库/git 备份 | 命中即拒绝并建议改记"存放位置" | **误伤**：合法但形似密钥的内容被拒（示例 token、测试夹具） |
| **A11 注入框架/纠错**（**拆三块**，复核 §2.3） | 模型更愿意忽略无关记忆、能主动纠错 | 提示词与 hint 文案变化（行为层）；**护栏那一块删掉**——mem 的 hint 只注入一行固定文案、不注入记忆正文（`hints.ts:26-27` + `lexical.ts:57` 布尔），`stripInjectedMemory()` 在 mem 无对应物 | 文案过长会挤占系统提示词预算；真实回环是"recall 输出被记回去"，改用来源口径守 |

### 2.2 不新增能力、但改变结果的项

| 项 | 功能性后果 |
|---|---|
| **F4** FTS 改覆盖率打分 | 长笔记的偶然命中不再占前排 → 短事实更易进 top-k；对"全库匹配"的查询影响最大 |
| **A5** 乘性 boost | 近期/高信任/多证据的事实小幅前置（±10% 量级），**不会**越过主相关性 |
| **A8** 预算装箱改"跳过继续/整条返回" | 返回集组成变化：更少"半截文本"，可能出现"更长但更少"的条目 |
| **F2** router 分数上报口径 | 模型看到的分数语义变化（去掉 min-max 后不再"top-1 恒 1.0"）→ 模型更可能说"没找到" |
| **A3** 实体规范化 | 同一实体的多种写法归并 → 实体腿召回更干净、`related/probe` 更准 |
| **A4** 索引文本并入实体名/日期 | 关键词腿能按实体名命中（即使正文没写全名） |
| **A10** 确定性图边 | 多跳（时间/实体相邻）可达；与 HRR 探针职责重叠，需 A/B |
| **L3/L4/L2** | 目标是精度/排序，不新增能力；L2 若保留会**删掉单腿强命中**（功能回退） |
| **E0/A12/A13/A14/A16** | 不改用户可见功能（A13 提升内部一致性；A16 只是把已有旋钮打包） |

### 2.3 跨库（kb）的功能风险

`entities/extract.ts` 与 `store/hybrid.ts` 被 memory 与 knowledge 共用 ⇒ **A2/A3/A4/A6/A7 会同时改变 `kb_query`
的行为**，而 **kb 没有冻结评测集**。功能回归风险集中在 kb：每批必须附一次性 kb 对照（≥10 条查询的前后 id/顺序）。

### 2.4 哪些项**真的**提升"事实召回精准度"（逐项诚实判定）

| 判定 | 项 | 依据与前提 |
|---|---|---|
| **可能真提升，但要 A/B**（唯一直接打已记录病理的项） | **F4** FTS 改覆盖率打分 | 2026-10-04 事故的病根是"bm25 在 OR 三元组上奖励偶然含多个查询碎片的长笔记"；覆盖率是**长度中性、绝对**的，且 `countMatchedTerms` 已在地板里算过（近免费）。**反方**：naive 覆盖率会丢掉 bm25 的 IDF（常见查询词被过度加权），所以候选实现是**混合**（覆盖率 × IDF 或归一 bm25），A/B 必须含这一变体 |
| **可能提升，证据弱** | **A3** 实体规范化 | 实体袋更干净 ⇒ 锚点更少更准、扇出下降；但 b900b46 的锚点/饱和并集已经修过一轮，边际增益未量化，且**过度合并会伤召回** |
| **查询类能力（非整体精准）** | **A2** 时间腿 | 只改善**带时间表达**的查询（今天这类查询完全忽略时间）；对普通查询如果不加该腿自己的门槛，反而**多进候选** |
| **只动排序尾部的 ±10%** | **A5** 乘性 boost | 设计上就不能压过主相关性；能改善"近期/高信任/多证据"的次序，**不是精准度修复** |
| **只改善"答案层"的观感，不改检索** | **F2**（分数语义诚实）、**A8**（整条装箱） | F2 让模型能判断"这只是本次最不烂的一条"；**A7 要小心**：hindsight 的 `final` 门槛建立在它自己的融合分上，而 mem 的融合分**只是查询内相对量**——mem 的弃答应当继续钉在**每腿绝对原始分**（现有机制就是对的），不要照搬 final 门槛 |
| **不改检索，但让"更精准"可被证明/诊断** | **E0/A12**、**A6** | E0 已证明"冻结集看不见真实病理"；A6 让"这条靠哪条腿、几分"可见——**没有这两项，任何"更精准"都只是断言** |
| **不提升，甚至降低** | **L2**（交集式准入删单腿强命中）、**F1**（加弱尾换召回）、**L4①**（词典实测≈0/负）、**L3**（未证，K 次抽签可能放大长文） | 见 §2.2 与对照文档 |
| **与精准度无关** | A1、A11（行为/安全）、A9、A13、A14、A15、A16 | 内部结构、配置或性能 |

**对用户报告的那个症状（"3 条里 2 条不相关"）**：这批改进里**没有一条能直接修它**——正确答案本来就在 rank-1，
问题是"**相关但不回答问题**"的尾巴。能修尾巴的只有三类：**交叉编码重排**（需要模型，0.5.0 刚整体移除）、
**按属性/意图的准确分组**（L1，前提未证）、**呈现与弃答层**（F2/A8 + 正确的绝对门槛）。
⇒ 结论：这批改进提升的是「**可测量性 + 若干查询类的能力 + 排序细节**」，**不等于"事实召回整体更精准"**。

## 3. 性能影响

三维度：**每次读 / 每次写 / 常驻·启动·后台**。量级：`0`≈免费、`µs`、`ms`、`×N`（随规模放大）。

### 3.1 每次读（单次 search；跨库 ≈ 两 store 之和）

| 项 | 增量 | 量级 | 主导项与理由 |
|---|---|---|---|
| **F1** 放宽档触发 + 并集 | **第二遍完整腿集**（腿的 SQL + fuse + 取文本），在"命中数 < k"的查询上触发 | **×1.5–2**（触发面待测） | 现状只在"严格档返回 0 条"时触发（罕见的早退路径 0.35 ms）；F1 把触发面扩到"不满 k"，会覆盖大量常见查询。**必须先测触发率** |
| **A2** 时间腿 | +1 条腿（窗口重叠查询）+ 规则解析 | `ms` 级（有索引）/ 规则 ~0.1–1 ms | 若 `occurred_at` 无索引 → 扫描；解析必须**不进 `relevance()` 同步路径**（见 §3.4） |
| **A10** 图腿 | +1 条腿（多跳遍历）+ 每跳 join | `ms` → `×N`（无索引时） | 对照教训：HRR probe 在 33k 时 **1366 ms**——图腿若无索引 + 硬上限会重演 |
| **A4** 索引文本变长 | FTS 每匹配行的打分更贵 | `ms` → `×匹配数` | FTS5 为**每个匹配**打分再 LIMIT：行数不变时，每行的词元更多 ⇒ 常见词查询最吃亏 |
| **A6** 逐臂分 | 序列化体积（每 hit +4 字段） | `0`（CPU）/**默认 0 token**；显式 `include_scores` 打开时每 hit +30–60 token | 默认关 ⇒ 日常调用零税；脚本/UI/E0 显式打开。**这是给模型付的钱**，不是 CPU |
| **A5 / A7 / F4 / F2 / A14 / A16** | 池内乘算 / 过滤 / 已算过的词数 / 去归一化 / 融合方式 / 配置映射 | `0`–`µs` | `countMatchedTerms` 已在地板里算过（F4 近免费）；A5 在已排序的池上做乘法 |
| **A15** cap-then-hydrate | 少解码被丢弃的文本 | 略微**变快**（SQLite 下收益小） | 无网络往返，收益主要在超大文本 |
| **A3** 实体规范化 | 实体袋更小/更一致 ⇒ 锚点候选更少 | 可能**变快** | 实体腿扇出（评审表：常见词 6600）随袋宽下降 |
| **L2/新门槛** | 若增加"资格过滤"→ 池变小（快）；若只改排序 → `0` | `0` | 但功能上会丢候选 |

### 3.2 每次写（remember add/update、kb ingest、reindex）

| 项 | 增量 | 量级 | 理由 |
|---|---|---|---|
| **L3** 长事实分块 | **嵌入 ×(1+K)** + 向量存储 ×K | **×2–4**（300 字符 ≈ 35 ms/块） | 写路径的支配项就是嵌入（33.7 ms/chunk 实测） |
| **A3** 实体规范化 | 每次写入加"实体解析"（trigram 比较 × 候选上限） | `ms` 级 | 有候选上限，可接受；但**版本号一升就是全库重扫**（见 §3.3） |
| **A4** 索引文本并入 | FTS 插入文本 +30–60%（实体名 ~31 个 + 日期 token） | `ms` 级 + 索引字节 ↑ | `facts_au` 触发器**每次 update 重写全文**；external-content 表还要新增真实列（文本再存一份） |
| **A10** 图边 | 每事实插入若干边（有上限） | `ms` 级 | 时间边/实体边是确定性插入；因果边留给写侧 |
| **L1/B1** 标签 | 调用方直接给 → 几乎 0；引擎抽取 → 一次抽取成本 | `µs`/`ms` | 回填是一次性全库扫描（见 §3.3） |
| **A1** 密钥扫描 | **44 条** regex 过一遍 content（模式表 `extensions/memory_defense.py:167-238`，已核） | `µs` 级 | 313 字符 × 44 模式，可忽略 |
| **A9/A13** | 多一列 / 快照一行（上限 50/条） | `0` / 写入 +1 row | A13 快照有界 |
| **E0/A12/A11** | 无运行期写入成本（A11 只是一次会话一次的提示词） | `0` | |

### 3.3 常驻、启动与后台

| 项 | 增量 | 量级 | 理由 |
|---|---|---|---|
| **L3** | 向量数 ×K ⇒ vstore 常驻 ×K、索引重建 ×K、启动 ×K | **×K** | 768 维 ≈ **3072 B/向量**（84 条现在 <0.3 MB，但 33k 条 ×3 块 ≈ **304 MB**）；`buildRuntime` 已实测 763 ms@2k → **14688 ms@16k**，×K 会把它再放大 |
| **A4** | FTS 索引字节 ↑（+30–60% 文本对应的 trigram） | 磁盘 ↑ | 外部内容表不复制正文，但**新增真实列会复制一份文本**；两者都计入 db 体积 |
| **A10** | 边表（fact↔fact）字节 | 磁盘 ↑（与边数成正比） | 需要索引才能不退化 |
| **A3 升版本** | **一次全库重抽取**（有界、可续跑） | 一次性总 CPU = N × 单条实体成本 | 通道已就位（`entities_version` 扫描）；规模上等于把"33k 条 × 实体抽取"跑一遍 |
| **A13** | 快照表 + 水位线查询 | 磁盘 ↑（受 50/条 上限约束）/ 查询 `0` | 水位线是一次索引 `MAX(updated_at)` |
| **E0/A12** | 夜间真模型作业（CI 时间与费用） | 非运行期 | 不占用户路径 |
| **A2**（若含确定性时间边） | 边表 + 写入期插入 | 磁盘 ↑ / 写 `ms` | 与 A10 同批最省 |

### 3.4 一个独立的"每次用户消息"热路径：hint

`relevance()` 在**每条用户消息**上**同步**执行（`plugin/src/index.ts:750-775`），且**不能 await 模型**。
因此：

- **A2 的时间解析不要放进 `relevance()`**——它属于查询路径；如果为了"时间类 hint"而在这里加规则解析，
  每轮都要付 CPU，且会与"同步、纯字符串"的既有纪律冲突。
- **A11 的文案会加长 hint/系统提示词**——按 token 计费（每轮一次），要控制在几十 token 内。

## 4. 三张账单（可直接进性能验收）

**① 每次检索**（新增项）

| 项 | SQL 次数 | 每腿匹配行数 | fuse 池 | 返回 hit | tool 输出字节/token |
|---|---|---|---|---|---|
| A2 | +1 | ≤cap（窗口） | +≤200×遍 | 不变 | ≈不变 |
| A10 | +1×跳数 | ≤cap | +≤200×遍 | 不变 | ≈不变 |
| F1 | **×（1→2）** | ×2 | ×2（并集） | ↑（弱尾） | **↑** |
| A6（默认关） | 0 | 0 | 0 | 不变 | 默认 0；打开 +30–60 token/hit |

**② 每次写入**：`tagText` + 实体/三元组/HRR + **嵌入（支配项）** + FTS/边/快照维护。
A1 `µs` / A4 `ms + 索引` / A3 `ms + 一次性全库` / A9 `0` / A13 `+1 row` / **L3 `嵌入 ×(1+K)`**。

## 5. 组合画像（按建议批次）

| 批次 | 性能后果 |
|---|---|
| **0–1（E0/A12 + A6 + A1）** | 运行期 CPU ≈ 0；A6 默认关 ⇒ 默认零 token（打开时每 hit +30–60）；A1 是 µs 级 |
| **2–3（L2 重写 + F4 + A5/A7/A8/F2/A16）** | 读路径基本不变；A8 略省（少 truncate）；L2 若只改排序则 0 |
| **4（A2 + A4 + F1）** | 读路径首次出现**实质增量**：+1 腿、FTS 打分变重、**F1 可能把平均读成本抬 1.5–2×**；写路径 +边/索引文本 |
| **5–6（A3 + A13 + A9 + A10 + B1/B2/B3）** | 一次全库重扫（A3）；A3 之后实体腿**可能更快**；A10 加一条需索引的腿 |
| **7（A1/A11）** | ≈0（A1 µs，A11 token） |
| **L1/L3 完整实现** | **数量级**：L3 = 嵌入/向量/启动/RSS ×K；L1 = 查询返回"一组" + 一次全库回填 |

**共同原则**：每条新腿都必须满足"**有索引 + 有硬上限 + 参与 fuse 的候选受 `legCap` 约束**"，
否则会把 HRR probe 那 1366 ms@33k 的病复制一遍。

## 6. 必须先建的性能基线（怎么量、量什么）

1. **每次检索**：SQL 次数、**每腿匹配行数（扇出）**、`fuse` 池大小、返回 hit 数、tool 输出字节；
   分"选择性 / 常见词 / 零命中 / 时间窗 / 自指"五类查询。
2. **每次写入**：`tagText` / 实体+三元组 / HRR / **嵌入** / FTS / 索引维护分项。
3. **启动**：`buildRuntime`、`reloadIndex`、首次后台扫描；分"冷 / 温（有索引缓存）"。
4. **常驻与磁盘**：RSS、**vstore 条数×维度**、`memory.db`、FTS 与边表字节。
5. **三个规模点**：复刻 `PERFORMANCE_REVIEW.md` 的 2k / 10k / 33k（kb 侧 299 / 4499 chunks）。
6. **触发率指标**（比 p50 更能防退化）：F1 第二遍触发率、A2 时间窗命中率、A3 实体合并率。
7. **回归门**：`p50/p95 不变差` **且** `扇出有界、SQL 次数不超预算` —— 只盯 p50 会漏掉"扇出悄悄变全库"。

## 7. 结论：按性能代价排序的落地建议

| 档 | 项 | 性能判断 |
|---|---|---|
| **近免费**（可直接做） | E0/A12、A6（默认关；打开才付 token）、A1、A11、A5、F4、F2、A7（默认关）、A9、A13、A14、A16 | CPU `0–µs`；A6 默认零税 |
| **可能变快** | A3（扇出↓）、A15 | 但 A3 要付一次全库重扫 |
| **需先测触发率才敢上** | **F1**（第二遍覆盖多少查询）、A2（新腿+索引）、A4（索引膨胀）、A10（多跳+索引） | 都是"触发面 × 单次成本"，触发面未知就不要排期 |
| **数量级、必须单独设计** | **L3**（×K 向量/嵌入/启动/RSS）、**L1/B1**（返回一组 + 全库回填）、A10（若不做索引） | 先做离线原型 + 规模点实测，再谈落地 |
| **会拖慢且无功能收益** | L2（保留版）、L4①（词典） | 建议不做 |

> 一句话：**这些改进对 mem 的性能影响不是均匀分布的**——四条前置项（E0/A6/A1/A11）几乎不花钱，
> 而 **L3 与 F1 是唯二能改变数量级/触发面的项**，必须在动手前把 §6 的基线建起来；
> 所有新腿的验收都必须包含"**扇出有界**"这一条，而不是只看 p50。
