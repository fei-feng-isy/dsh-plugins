## 0. 结论速览

**① 重排 A/B（`none` vs `bge_reranker`）**

1. **`bge_reranker` 今天完全不生效**——这不是"效果一般"，是**两处互相独立的缺陷**让每一次重排都原样退回融合序：
   - `LocalReranker` 把 `[query, doc]` 的**嵌套数组**交给 transformers.js 的 `text-classification` pipeline，
     而 pipeline 内部固定调用 `tokenizer(texts, {padding, truncation})`（没有 `text_pair` 分支），tokenizer 在
     `normalize()` 里对数组调用 `.replace()` 直接抛错；适配器 `catch` 后返回**原顺序**（identity）。
   - **即便把调用形状改对**，该模型 `num_labels = 1`，pipeline 对单 logit 做 softmax 恒为 **1.0**；
     `extractScore` 于是给每个候选同样的 1.0 → 稳定排序 → **仍是融合序**。
   实测：55 条查询 × 每条 3 次重排，**179 次** `rerank: inference failed — keeping fused order: text.replace is not a function`；
   两臂排序 **55/55 逐条相同**（脚本断言 `production_adapter_identity_everywhere: true`）。
2. **代价却照付**：模型目录 **1,129,558,892 B（1077.2 MiB）**，
   首次下载+加载 **52.86 s**，之后进程内加载 **2.88–9.46 s**；健康计数 `rerank_used = 14`、`rerank_fallback = 0`
   ——**计数说"用了重排"，而排序一次都没动过**。
3. **把同一份权重正确接线**（`tokenizer(query, {text_pair: doc})` + 直接取 `model.logits`）后，**能力是真的**：
   痛点查询 `我是谁？` 上，正确的 cross-encoder 给 #4（9 字符身份事实）**logit −2.72**，其余候选全部 ≤ −6.00。
   但它**修不了这次的 top-3**：#103（53 字符，−8.50）被从第 3 名压到第 6 名，
   **#117（67 字符，−6.98）仍留在第 3 名**，并且把一个**同样非 gold** 的 #133（170 字符，−6.00）抬到第 2 名
   —— **top-3 相关条数 1 → 1 不变**。代价 **~17 s/查询**（real p50，见 §2.6）。
4. 更广的读数也不支持默认开启：冻结 41 条 top-1 **41/41 → 39/41**（2 条被 CE 弄错），真实库 top-1 10/11 不变、
   top-3 相关均值 **1.82 → 1.64**；`must_exclude` 27/41 → 28/41（唯一的小改善）。
   **结论：现状不建议开启 `bge_reranker`（开了等于白付 1.05 GiB + 冷启 + 一个会撒谎的计数器）；即便修好接线，本库上也不值得默认开启。**

**② 语义门槛 0.50 vs 0.55（本机真实库，20 条查询）**

1. **0.55 砍掉的条目里，没有一条是已声明的真答案。** 真实库：语义窗口内 `0.50 ≤ cos < 0.55` 的候选共 **54 条**，
   与 gold 的交集 **0 条**；真正改变了最终 top-5 的 **20 条**里，gold 也是 **0 条**。
   冻结集口径：`must_include` **40/41 不变**，`must_exclude` **0.6585 → 0.6829**（多一条被正确排除），P@k / R@k / MRR / empty_rate 全部不变。
2. **严格档非空率 18/20 → 17/20**：`插件怎么安装` 在 0.50 下只剩 1 条（#108，cos 0.5191），0.55 下**变空**。
   **默认档（自动放宽）20/20 → 20/20 不变**——但这不等于"没变化"：该查询在 0.55 下严格档空 → 触发放宽档 →
   返回 **5 条**（而非 0.50 时的 1 条）。**放宽档把"变空"换成了"多召回 4 条弱命中"。**
3. **top-1 变化**：严格档 2 条（`插件的安装方法` 122→108；`插件怎么安装` 108→空），默认档 1 条；**都不涉及 gold**。
4. 对用户点名的痛点：`我是谁？` 在 0.55 下 **#117、#103 同时被挤出 top-5**
   （两条的**有效语义余弦** 0.5173 / 0.5157，都 < 0.55；注意 0.5328/0.5315 是它们的**融合分**，不要混用），
   但替补进来的是 #25 / #36 / #43 / #64（同样非 gold），**top-3 相关数仍是 1**。
   **0.55 能"清掉 #103/#117"，但清不掉"非 gold 长条目占位"这个结构问题。**

## 1. 方法与纪律

- **只读真实库**：`~/.avantf/memory/memory.db` 全程以只读连接打开，用 `VACUUM INTO` 生成一致性快照；
  重排 A/B 每个臂**各用一份快照**（召回会写"强化"，分臂避免互相污染）。
- **只读真实配置**：每个 runtime 的 `dataHome` 指向临时目录，`configs/common.yaml` 由脚本现写；
  `~/.avantf/configs/*.yaml` 一个字节都没读/写。
- **两臂同候选集**：只改 `rerank.backend`（`none` / `bge_reranker`），腿、权重（0.55/0.30/0.15）、门槛（0.50）全部默认。
  重排臂看到的是 `limit × over_fetch_factor`（默认 5）的**过取池**；脚本用 `over_fetch_factor: 1` + `limit = k×5`
  复现出**逐条相同**的池（断言 `pool_topk_matches_none: 55/55`）。
- **查询集**：
  - **真实库 14 条** = 6 自指（`我是谁？/我叫什么/我的名字/我是做什么的/我叫啥/本人是谁`）
    + 3 非自指对照（`插件的安装方法/生产环境的部署流程/数据库主从延迟`）
    + 5 条 2 字实体型（`插件/任务/版本/宿主/会话`）。2 字查询的 gold = **实体集里含该词的活跃事实**（实体腿自己的目标）。
  - **门槛任务再加 6 条常见问法**（`插件怎么安装/记忆库在哪/检索权重是多少/模型怎么换/数据根在哪/任务怎么调度`）→ 20 条。
  - **冻结集 41 条** = `packages/core/test/fixtures/eval_zh_relations.jsonl`，驱动方式同 `scripts/bench-floors.mjs`
    （每个 case 一个临时 runtime、真 `remember` + 真 `recall`、真嵌入模型）。
- **隐私**：默认**不打印正文**；只有 §3.2 被 0.55 砍掉的条目按用户要求打印**前 24 个字符**（标注 `head24`），
  用于判断"砍掉的是不是真答案"。**这是本报告唯一的正文泄露面**；`--no-head` 可关闭。
- **实测 vs 推断**：见 §4。
- **本机口径**：Node v22.23.2；12 逻辑核；测量期间 1 分钟负载 1.56 → 6.02（脚本记录 `loadavg`），
  延迟数字含共享主机的噪声（每条查询重复 3 次取中位数）。
- **同一份构建产物**：两次测量都读 `mem/packages/*/lib`（构建时间 **2026-10-04 23:15:51**，早于两次运行）；
  期间另有 E2 车道在 `mem/packages/**` 施工，本任务**只读、未改、未重建** `packages/**`，所以两轮读数落在同一份代码上。

## 2. ① 重排 A/B（`none` vs `bge_reranker`）

### 2.1 结论性发现：`bge_reranker` 今天是 no-op（实测 + 最小复现）

实测（同一进程、真模型、走生产适配器 `LocalReranker.rerank`）：

```text
[avantf-mem] INFO rerank: reranker ready Xenova/bge-reranker-base (2957ms)
rerank: inference failed — keeping fused order: text.replace is not a function
ORDER [4,103]        # 输入 [4,103] → 输出 [4,103]，模型一分没改
```

缺陷一（调用形状）：`adapters/local_reranker.ts` 传 `[[q,d], ...]`，而 transformers.js 4.3.0 的
`TextClassificationPipeline._call` 固定执行 `this.tokenizer(texts, {padding, truncation})`；
`PreTrainedTokenizer._call` 对"数组里的数组"没有 pair 分支，`_encode_plus([q,d])` 把数组送进
`normalize()` → `text.replace is not a function`。适配器 catch 后 `return candidates.map(c => c.id)`。

缺陷二（分数恒为常数，代码级推断 + 实测旁证）：
`bge-reranker-base/config.json` 是 `num_labels: 1` 且**没有 `problem_type`**，
pipeline 走 `softmax(single logit)` → 恒 `1.0`。实测旁证：对同一模型调用 pipeline 的单文本路径，
两条语义完全不同的文本都返回 `{"label":"LABEL_0","score":1}`，而底层 `model.logits` 是 `-4.50 / -1.12`。
所以即使修好缺陷一，`extractScore` 仍会给所有候选 1.0。

**这两点都在 `mem/packages/**` 里，本任务按要求只读、不改。**

副作用（实测）：`rerank_used = 14`、`rerank_fallback = 0`
（`queries = 203`）。`rerankState()` 的判据是 `configured && isAvailable()`，
而"模型加载成功"与"这次真的重排了"是两回事——**计数器在它专门用来暴露的那种情形里说了假话**。

### 2.8 ①结论（回答题面三问）

- **能否把 #103/#117 这类"嵌入分高、语境无关"的条目压下去/挤出前 3？**
  - **按现状（`rerank.backend: bge_reranker`）：不能，一条都压不下去**——重排根本没跑（identity）。
  - **按正确接线：一半。#103 被压到第 6，#117 仍在第 3**，并且 #133 补位到第 2；`我是谁？` 的 top-3 相关数 1 → 1。
    更广地看，正确 CE **略伤**冻结集 top-1（41→39）与真实库 top-3 相关均值（1.82→1.64）。
- **代价多少？** 现状：+**1,129,558,892 B** 磁盘、+2.9–9.5 s 冷加载、每次查询一次注定失败的
  tokenizer 调用（<2 ms，但每条查询都记一次 `rerank_used`）。正确接线后：**真实库 p50 ≈ 17.33 s / 查询**，
  且随过取池（`limit × over_fetch_factor`）与正文长度线性增长。
- **是否值得默认开启？** **不值得**。现状是"白付磁盘 + 假计数"；修好接线后是"慢 17 s/查询，换来略差的 top-1/top-3"。
  如果目标是"把 #103/#117 挡掉"，**0.55 门槛在本次测量里更便宜、更有效**（见 §3），
  而 CE 的价值（把 #4 与其余拉开到 −2.72 vs ≤−6.00）在本库已经被方案 A 的改写路径覆盖。

### 3.5 ②结论

- **0.55 砍掉的条目里有没有真答案？**
  - **真实库（本次 gold 口径）**：机制口径 54 条里 **0 条 gold**；可观察的 20 条里 **0 条 gold**。
  - **冻结集口径**：`must_include` 40/41 不变、P@k/R@k/MRR 不变、`must_exclude` 反而 +1。
  - **判断标准（人工）**：可观察砍掉的条目按 `head24` 看，基本都是"同主题但不同问题"的长笔记
    （如 `插件的安装方法` 砍掉的 #159 是 npm registry 现状、#29 是 profile 配置、#109 是工具面清单）；
    **没有一条是那条查询的直接答案**。注意 #117（敏感信息口径）本身就是**用户自己要求"另存/不外泄"的约定**，
    出现在 `我是谁？` 的 top-3 是嵌入分误伤，**砍掉它是收益而不是损失**。
- **非空率/top-1 是否变化？** 严格档非空 18→17、top-1 2 条变化；默认档非空不变、top-1 1 条变化；
  **所有变化都不涉及任何 gold 答案**。
- **建议**：0.55 在本次 20 条 + 冻结 41 条上是**净收益**（清掉 #117/#103 这类长干扰、`must_exclude` 提升、
  零 gold 损失），代价是"更依赖自动放宽档"（严格档更容易空 → 放宽档更容易触发，表现为"多召回弱命中"）。
  **是否改默认仍是派单方的决定；本轮不改任何配置。**

## 4. 实测 / 推断 / 没能验证

**实测（本机、本次运行）**
- `bge_reranker` 每次 `rerank()` 抛 `text.replace is not a function` 并返回入参顺序（179 次记录，55 条查询 × 3 次 + 14 次 runtime 调用）。
- 两臂排序 55/55 逐条相同；`pool_topk_matches_none` 55/55。
- R2（`text_pair` + 原始 logit）的排序、logit 分数、top-1/top-3、延迟、体积、下载/加载时长。
- 门槛 0.50/0.55 的 20 条真实库读数、54 条候选的 cos、冻结 41 条的 7 项汇总。

**推断（有代码/数据依据，但未直接观测到输出）**
- "即便修好 `text_pair`，`num_labels = 1` 的 softmax 也会让 `extractScore` 恒返回 1.0"：
  依据是 pipeline 源码的 `function_to_apply` 分支 + `config.json` 无 `problem_type`，
  以及**同一模型** pipeline 单文本路径实测返回 `score: 1`（而底层 logits 是 −4.50/−1.12）。
  没有把修复打进 `packages/**` 去端到端验证——这是本任务的禁令。
- R2 的延迟是在**共享主机**（1 分钟负载 1.6→6.0）上测的；换到空闲机器可能更快，但 12 层模型的量级不会变。

**没能验证 / 未覆盖**
- 没有测 `knowledge` 库（文档切片）的重排——本任务的题面是记忆库；知识库走同一 `rerankHits`，结论应同构，但未实测。
- 没有测"正确接线"下**过取因子**（`over_fetch_factor`）对 CE 质量/延迟的敏感性；只用了出厂默认 5。
- 没有测 `rerank.max_input_tokens`、batch 大小、量化 dtype（`model_quantized.onnx`，体积/速度小得多）等旋钮。
- 真实库 gold 是**本报告自定义**的（自指问题指向 pinned `user_profile`；2 字问题指向实体集），不是官方标注；
  3 条非自指对照**没有 gold**（按题面要求单独列出、不硬凑）。
- 门槛任务的 20 条查询不是冻结集；冻结集结论只覆盖 `eval_zh` 的 41 条。
- 没有验证修复后重排对**放宽档**命中的影响（0.55 下放宽档返回的弱命中是否会被 CE 重排改变）——本次 R2 只看严格/默认档的过取池。
