## 0. 要回答的唯一问题

**今天的关系能力够不够用？** 具体三问：
① 现有关系载体（`triples` / 事实↔实体 / 矛盾 / 修订链 / HRR）的质量是什么水平？
② 五个关系动作（`chain` / `probe` / `reason` / `related` / `contradict`）**今天能不能回答问题、答得对不对**？（当前**零基线**）
③ 若答不出，缺口是"**缺关系**"、还是"**有关系但没有遍历/读者**"、还是"**关系是错的**"、还是"**语料里根本没有**"？

**本卡只测不实现**：不建关系表、不加腿、不改工具。

## 1. 红线（沿用第四/五轮协议，逐条可检查）

只读快照 + 临时 dataHome；**正文只在进程内读**；**凡从正文派生的字符串（问题、实体名、判定结论）一律落 `/tmp`**；
仓库产物只放**聚合**；写前过敏感模式扫描（`hindsight-api-slim/hindsight_api/extensions/memory_defense.py:167-238` 超集）

## 2. S1 · 三元组画像（无标签 + 抽样人工判定）

- 全库 `triples`：每条事实的条数分布；**谓词分布**；`STOP_PREDS` 命中与丢弃比例；
  `subj`/`obj` 是"实体名"（能对上 `entities`）还是"片段"的比例；**抽样 20–30 条人工判定准确率**（注明判定方法）。
- 与实体层对照：同一批事实的 `fact_entities` 数量，判断三元组是**补充**还是**噪声**。

## 3. S2 · 五个关系动作的基线（零基线，本卡的核心）

对 `chain` / `probe` / `reason` / `related` / `contradict` 各构造一组**真实语料问题**（每个动作 ≥10 条：

- `chain`：从真实事实里挑一条 SPO，问"这个主体的这个属性/下一步是什么"；
- `probe`：给一个真实实体，问"关于它我们知道什么"；
- `reason`：两个真实实体联合，问它们的共同点/关系；
- `related`：给一个实体，问"还和哪些实体相关"；
- `contradict`：构造一对真矛盾与一对假矛盾（正反例都要）。

指标：**能否给出答案、答案对不对、错在哪**（人工判定，抽样上限 30 条，注明方法）；
并记录**并集是否收窄**（若某动作只能靠过滤实现）。

## 4. S3 · 需求侧：多跳与关系浏览问题（现有机制下能答多少）

- 从真实语料**反推**两类问题（沿用第四轮派生引擎的两条硬规则：**查询不得含 gold 的唯一字面**；带无时间/无关守卫）：
  1. **多跳问题**（需要两条以上事实串联，如"A 的负责人所在的项目"）——构造时记录**需要哪几条 gold 事实**；
  2. **关系浏览问题**（"和 X 相关的事实"）——gold = 与 X 共享锚点实体的那组事实。
- **只用现有机制**（`recall` 的 search/ask/chain/reason/related，生产配置，默认参数）测：
  `gold 全在 top-3` / `部分在` / `全不在`、`missing`、平均名次；**并给出 identity 断言**（脚本 pass == 生产）。

## 5. S4 · 归因（把失败分到四类，计数）

对 S3 中"全不在"的每一条，判定原因（各给判据与口径）：

| 归因 | 判据 |
|---|---|
| **A 语料里没有** | gold 事实本身不存在（或不在 active 集） |
| **B 无连接** | 存在 gold 事实，但两/多条之间**没有任何**现有载体相连（无共享实体、无三元组、无矛盾、无替代） |
| **C 有连接但无遍历/读者** | 连接**存在**，但现有动作不会沿它走（例如共享实体存在却只能靠过滤） |
| **D 连接是错的** | 载体存在但内容错（三元组噪声、实体归错） |

## 6. S5 · 引擎可派生边的覆盖（决定"要不要 agent"）

对 S3 的每条多跳/关系浏览问题，在脚本里**只允许**用四类**引擎可派生**的边
（`shared_entity` 按共享锚点实体 / `temporal` 按时间窗 / `supersedes` / `contradicts`）判断：
**这些边能不能把需要的 gold 事实连起来？** 给出比例，并列出"连不上"的那些各需要什么类型的关系
（如 `causal` / `same_as` / `belongs_to`）——**这是"引擎派生够不够、要不要调用方声明"的唯一依据**。

## 7. 预注册判据（先写、后执行；改判据必须如实记录）

- **若现有机制已能答**（多跳 `gold 全在 top-3` ≥ 约定阈值，建议 **≥70%**；关系浏览同）⇒ **关系层不做**，本线关闭。
- **若答不出，且 S5 显示四类可派生边能把 gold 连上（建议 ≥70%）** ⇒ **采纳"引擎派生关系层"**（确定性、零 LLM、零调用方负担）。
- **若答不出，且缺口主要是不可派生类型（`causal`/`same_as` 等）** ⇒ 才考虑"调用方声明"的窄形态，并给出该缺口的**规模与占比**。
- 三种结论都要给**数字**；S4 的 A 类（语料里没有）**不计入**任何"要做的理由"。

## 8. 必答数字（交付与验收）

2. 五个关系动作的成功率/正确率（各自）；
3. 多跳与关系浏览问题在**现有机制**下的 `top-3 全中 / 部分 / 全不中` 与 `missing`；
4. S4 四类归因的计数与占比；
5. S5 四类可派生边的覆盖率 + "连不上"所需的边类型分布。
