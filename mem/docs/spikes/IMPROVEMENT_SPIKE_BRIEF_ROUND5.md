## 0. 要测量的最终形态

**写侧**：agent 在调用保存之前，把要记的内容**拆成 N 条原子事实**，并在**同一次工具调用**里连
**它们之间的关系**一起给出（最终形态 = 一次调用 → N 条记忆 + 若干条关系）。

**本轮只测、不实现**：批量写入与关系声明**全部在脚本里模拟**（临时库副本 / 脚本内臂），
`mem_remember` 不动，关系层不建。

## 1. 红线（沿用第四轮协议，逐条可检查）

- 只读快照 + 临时 dataHome；**正文只在进程内读**；**凡从正文派生的字符串（拆出的原子文本、关系、问题）一律落 `/tmp`**；
  仓库产物只放**聚合数字 + 派生引擎（代码）+ 方法说明**。
- 写前过敏感模式扫描（`hindsight-api-slim/hindsight_api/extensions/memory_defense.py:167-238`，用超集）；
  产物 key 级自查 + **不得含 ≥8 字符 CJK 串**（术语白名单外）。
- 不改 `mem/packages/**`；不实现批量 `add`；不建关系表；不跑全量门禁。

## 2. S1 · 拆分语料与真值（前置；执行者当"拆分的 agent"）

- 取样：真实库里 **`length(content) ≥ 200` 的 68 条**（已知分布：85 条 active、中位 313、p90 513、max 882）。
- 对每条**拆成 N 条原子事实**，逐条满足：① **自包含**（不得用"它/那个/上述"指代，必须带主体）；
  ② **只含一个断言**；③ 保留可判定的时间信息。
- 同时对同一批次**声明关系**（封闭枚举建议：`same_topic` / `causal` / `temporal` / `subsumes` / `contradicts`），
  并标注每条原子的"来源句"用于事后核验。
- **两遍独立拆分**（换措辞/顺序/温度，互不看结果）——用于 S4 的一致性。
- 落 `/tmp`；仓库只留产出率统计（每条平均几条原子、N 分布、自包含通过率）。

## 3. S2 · 质量臂（同一语料，只换写入形态）

| 臂 | 写入形态 |
|---|---|
| **A0 基线** | 现状：一条长事实（1 行） |
| **S1 拆分** | N 条原子（无关系）——检验"拆分本身" |
| **S2 拆分 + 关系** | N 条原子 + 批次内关系（**脚本内**模拟一条"关系腿"，只作一腿、不改融合权重契约） |

**查询集**（全部从真实内容派生，沿用第四轮的派生引擎与两条硬规则：查询不得含 gold 的唯一字面；带守卫）：
1. **每原子问题**：每条原子各派生一问（gold = 该原子）——检验"原子是否比长段更容易被精确命中"；
2. **跨原子问题**：需要**两条原子**才能回答（gold = 两条）——检验关系是否带来召回增益（S1 vs S2 的关键分离）；
3. **无时间守卫 + 无关守卫**。

**指标**：`top1 / top3 内 gold / missing / gold 进池`；**每次成功命中返回的字符数（token 效率）**；
实体袋中位宽与候选扇出；**默认不变**（不启用关系腿时，S1/S2 的检索结果必须与"仅这 N 条原子在库"逐字节一致）。

## 4. S3 · 去重与矛盾检测（用生产嵌入后端）

1. **去重**：对同一内容的**改写版**（paraphrase）分别以"长段"与"原子"形态写入，测
   `content UNIQUE` 命中率、以及近重复判定（`lifecycle/contradiction.ts` 的
   `EMBED_SIM_DUP_MAX=0.97`）能否抓到；报告"能被抓到的比例"。
2. **矛盾检测**：把一条被推翻的断言**嵌在长段中间** vs 作为独立原子，测
   `EMBED_SIM_MIN=0.75` 阈值的判定差异（同一生产嵌入后端，不下载模型）。
3. 两项都要给**反例**（不该命中的样本），避免把"更敏感"误当"更好"。

## 5. S4 · 关系的价值与一致性

- **S2 相对 S1 的增量**：跨原子问题的 `top1/top3/missing` 差；
- **边的类型分布**与每条原子平均边数；
- **两次独立拆分**的：边集合的重合率、关系类型的逐条一致率、以及"同一内容两次拆分后的**条数与边界**差异率"
  （第四轮实测写侧字段一致率很差：跨进程"至少一字段不同" 48.44%，本轮要给出拆分边界与关系的同类数字）。
- **结论必须回答**：关系若不一致，是"引擎可派生的类型"（共享实体/时间）能顶掉，还是必须由 agent 声明。

## 6. S5 · 批量调用的机制代价（临时库副本，脚本模拟）

在快照副本上分别执行：**① 一次事务插入 N 条** vs **② N 次单条插入**（今天的形态）：

- 写入延迟（总/每条）、WAL 增长、DB 增量；
- **返回形状**（N 个 id）与**部分失败语义**：当第 k 条违反 `content UNIQUE` 时，是全部回滚还是跳过该条？两种都测；
- 与既有机制的关系：`created_at` 单调性、修订链、实体重扫（`reindexEntities`）的预算、trust 首次结算；
- **契约税**：`add` 增一个数组参数的 schema 增量为多少字符/token（基线：`mem_remember` input schema
  **2623 字符 / 917 token**，第四轮已量）；对照"agent 分 N 次调用"的输入 token 差。
- **单次上限**：找出事务与响应体变得不可接受之前的 N（给出数字与理由）。

## 7. S6 · 失败模式（必须数字，不许只写定性）

| 失败模式 | 量什么 |
|---|---|
| **自包含性丢失** | 两遍拆分里含指代/省略且无法独立回答的原子比例 |
| **过度拆分** | 拆出的原子中"背离原意/无信息量"的比例（人工抽样判定，20–30 条上限） |
| **孤儿原子** | 兄弟原子被清理/归档后，单独存活的原子是否仍可理解（按既有 `idle_calendar_days`/purge 行为推演） |
| **行数膨胀** | 85 条 → 预计多少条；对 `stats`、清理、备份体积的影响 |
| **写入成本** | agent 为拆分与声明关系要多花多少输出 token（按字符计入） |

## 8. 预注册判据（先写、后执行；改判据必须如实记录）

- **采纳最终形态**：① 每原子问题 top1/top3 实质改善，且**每次命中的字符数下降**；
  ② 跨原子问题上 **S2 优于 S1**；③ 两次拆分的关系一致率达到**约定阈值（建议 ≥80%）**；
  ④ 没有不变量被打破（去重/矛盾/单调性/清理语义）；⑤ 给出 **break-even**：写侧多花的 token 需要多少次召回回本。
- **条件采纳**：仅拆分本身有效、关系无增量 ⇒ 只做"拆分 + 批量写入"，关系改为**引擎可派生的类型**（共享实体/时间）。
- **不采纳**：拆分在每原子问题上零位移，或写侧成本远大于召回节省 ⇒ 报告上限与原因。
