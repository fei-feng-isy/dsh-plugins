# capacity 派发闸门与 weight（2026-10-02）

> 目标：让"这台机器同时能跑多少活"由**引擎状态**保证，而不是靠派单者自己数并发；并且让"装不下"
> 表现为**排队**，而不是失败或拒绝。`DOMAIN_VERSION` 保持 1（新增字段带默认值），
> 既有守卫（unit 租约、`startingClaims`/`wakingClaims`、reclaim CAS、预算语义）一律不动。

## 一、要解决的问题

在 capacity 之前，引擎只有一个**槽位数**上限（`maxConcurrent`，默认 `CPU 核数 - 1`）：

- 它数的是**任务单元个数**，不是**机器负载**：两个"跑构建、编整个仓库"的任务和一个"读一个文件"的任务
  在它眼里完全一样，于是 12 核机器上两个吃满 10 核的任务可以被同时派出去。
- 节点没有任何"我大概会占多少"的申报面，派单者也无从写。
- 宿主那句硬件派生是**死代码**：`core/src/engine.ts` 里读 `process.availableParallelism?.()`，
  而 Node **从来没有** `process.availableParallelism` —— 真实 API 是 `os.availableParallelism()`。
  本机两者恰好都是 12，所以问题被掩盖；没有 `navigator` 的运行时直接掉到默认 4。
- 更根本的是**语义**：一旦发现装不下，最省事的写法是"拒绝受理"，但那是错的 ——
  一件已经交出去、已经建好树的事，不该因为"现在机器忙"而失败。

## 二、capacity：机器派生的容量（宿主边界）

### 2.1 优先级链

```
① config.capacity（显式，与 staleMs/roundMs 同层；按给定值夹取，不再减 1）
② os.availableParallelism()   // 尊重 cgroup CPU 配额与 CPU 亲和性
③ os.cpus().length            // 老运行时/拿不到配额时的退路
④ 默认 4
→ capacity = clamp(max(1, 派生 - 1), 1, 64)     // 预留 1 核给宿主 / UI
```

- 显式配置是**例外**：操作者给的数就是答案，静默再减 1 会让"配 4"变成 3。
- **预留 1 核**沿用家族既有口径（`cores - 1`）：引擎自己、owner 的回合、浏览器半边都在同一台机器上。
- **夹取 1..64**：容器报 4096 核也不该让引擎去物化几千个 claim。
- 实测（2026-10-02，开发机）：`os.availableParallelism()` = 12、`os.cpus().length` = 12、
  `/sys/fs/cgroup/cpu.max` = `max 100000`（无配额）→ capacity 11。

### 2.2 修掉死代码

`detectConcurrency()` 保留（`maxConcurrent` 的兼容语义：`cores - 1`、可被 `options.maxConcurrent`
覆盖），但**不再声称 `process.availableParallelism`**：core 没有 Node 类型，真正的机器读数只能由宿主做。
`detectConcurrency()` 退化为纯 `navigator.hardwareConcurrency ?? 4` 的顾问值，
真正的派生在宿主侧、走统一 API，算完作为 `EngineOptions.capacity` **注入 core**。

`capacity` 是 `EngineOptions` 的**必填**项：core 不猜硬件（猜出来的值不可注入、也不可确定性测试）。
宿主把派生结果注入；测试注入一个固定数字，于是每一条调度断言都是确定的。

### 2.3 `maxConcurrent` 与 capacity 的主从关系

| 闸门 | 语义 | 位置 |
|---|---|---|
| **capacity**（主）| 机器负载：`Σ running.weight + candidate.weight ≤ capacity` | `dispatch.ts` 的 `planDispatch` |
| `maxConcurrent`（从）| **槽位数**上限：同时最多几个任务单元，防止 weight=1 开太多会话 | 同上 |

两者**都满足才派发**。capacity 独立于槽位存在：槽位没满而容量不够 → 仍不派发（`waitingFor.reason = 'capacity'`）；
容量够而槽位满 → 不派发（`'slot'`）。

启动日志给出可诊断的一行：

```
engine ready: capacity=11 (source=availableParallelism, reserved=1) concurrency=11 depth=8 failure-budget=5 children<=6
```

`source` 取 `config | availableParallelism | cores | default`，是宿主派生链的取值来源，由纯函数
`deriveCapacity()` 给出。

## 三、weight：节点申报的重量

```ts
node.weight: number   // 这台机器上它会占用约几核（核当量，与 capacity 同单位）
```

- **默认 1**：不声明就是普通槽位，与既有行为逐位一致。
- **落点**：`create_mission.weight?` 与 `decompose_mission.children[].weight?`。入参文案面向使用者
  （"这件事大约会占几核"），不出现"树 / 节点"这类形状词。
- **子任务不继承父的估值**：父吃满 8 核，不代表它拆出来的每个前置任务都吃 8 核；继承会把刚拆开的
  并行度又串回去。缺省一律 1。
- **复用（去重）节点保留自己的 weight**：那是它在被创建时申报的值，可能正以那个重量在跑。
- **持久化 + 容错**：`NodeRecord.weight` 必填、值为数字；旧记录 / 脏值（字符串、`NaN`）在唯一载入边界
  `normalizeLoaded()` 与 `domain.ts` 的 schema 里都读成 **1**。`NaN` 尤其危险 —— 它与任何容量界比较
  都是 false，会让一个无界任务溜过闸门。
- **范围夹取**：`normalizeWeight()` 是唯一规范化函数（工具层、持久化、`makeNode` 共用），
  取整后夹到 `[1, 64]`。

## 四、派发闸门 ≠ 受理闸门

| | 受理闸门（不是本设计）| 派发闸门（本设计）|
|---|---|---|
| 位置 | `create_mission` / `decompose_mission` | `selectNextDispatchable` / `planDispatch` |
| 失败表现 | 拒绝调用 | **跳过**，节点留在 `ready` |
| 代价 | —— | **零**：不扣 `attempts`/`failures`/`spawnFailures`、无冷却、不记 `stalls` |
| 何时重评 | —— | 每次节点完成、每次 pass/sweep |

树建好、节点进 `ready` **就是排队**。这与 unit 租约的纪律完全一致（`unit-busy` 也是跳过不扣预算），
所以容量闸门和它同处一个函数、同一套记账。

`waitingFor` 因此**不进 `isTroubled`**：正常排队不是"反复出过问题"，owner 也没有可做的动作。

## 五、准入：work-conserving + 老化预留

### 5.1 work-conserving（装不下就跳过，继续扫描）

候选按**入队时间（FIFO）+ 老化提升**排序，**不按 weight 排序**。扫描时跳过装不下的重任务、
继续用轻任务填满空闲容量：capacity=4、running=2 时，队首的 weight=3 装不下（2+3>4），
它后面的 weight=1 仍会被派出去。否则一个重任务会白白空转一半机器。

### 5.2 老化 → 预留（防饿死）

一个节点被容量跳过的时间累计超过 `capacityWaitMs`（默认 **5 分钟**，下限 **1 分钟**）后进入**预留**：

- **不再接纳新节点**（已在跑的不动），等在跑的排空到它装得下，再派发它；
- 多个预留按**等待时间最久的先**（同刻按 FIFO）；
- 时钟来自 `EngineOptions.now`，测试注入即可确定性地推进。

**阈值取 5 分钟的理由**：短于此，一次普通的 weight=1 突发就会触发预留，而预留会立刻停止填充空闲
容量（重节点装不下时机器就闲着），把"防饿死"变成"平时就浪费"；长于此，重任务要等过一整个工作周期
才轮到引擎在它前面停止喂队列。下限 1 分钟是因为再短就与调度抖动无法区分。

### 5.3 独占例外（`weight > capacity`）

"要整机"的节点（申报重量大于整机容量）**只在无其它 running 时派发**：`runningCount === 0`。
它是"排得最久的预留"的算术形式 —— 永远装不下，只能等机器排空，所以**不会永远排不上**。
它同样按 5.2 老化：老化前它只是被跳过（轻任务继续跑），老化后预约整机，排空即派发，且**只派发一次**
（引擎在同一 pass 内先 mark 后返回，另一次 pass 看不到它）。

### 5.4 老化时钟的所有权

`deferredSince: Map<nodeId, time>` 由引擎持有（内存态）：重启丢一次等待起点、多等一个窗口，
不是正确性损失。节点被派发、离开队列（终态 / 拆解 / 取消）即清除，避免"旧起点导致复现即预留"。
被 unit 租约挡住、或只被槽位数挡住的节点**不计入容量等待**：那不是它的容量等待，
拿它去预约整机只会白等。

## 六、可观察：`waitingFor` 与限流日志

节点投影新增：

```ts
waitingFor: { reason: 'capacity' | 'unit' | 'slot' | 'aging'; resource?: 'cpu' | 'memory';
              needed?: number; available?: number; unit?: string } | null
```

- `capacity`：`needed` = 节点 weight，`available` = `capacity - runningWeight`（同一 pass 结束时刷新）；
- `slot`：`needed` = 1，`available` = 空闲槽位；
- `unit`：另一个 `running` 节点持有的范围（带 `unit` 名字）；
- `aging`：一个老化节点已预留整机，把这个候选挡在后面（无 `needed`/`available`，它等的不是空闲容量）；
- 内存下限门用 `reason: 'capacity', resource: 'memory'`，`needed`/`available` 是**字节**。

投影接到**面板行 / 详情**；`mission_result` 的 payload 里虽然带着 `waiting_for`，但读结果只在终态放行，
排队中的节点不是终态，所以那条通道**实际恒为 `null`**（`waitingFor` 是活状态，从不持久化）。
派发被推迟时打一条**限流**日志（每节点每分钟一条；**预留转变不受限流吞掉**，因为它改变了引擎的接纳行为）：

```
dispatch deferred: <node> needs N, capacity C, running R, waiting Ns[, reserved (no new dispatch until it fits)]
```

**等待也要告诉执行者本人。** 面板上的 `waitingFor` 是给 owner 看的；被派发的 worker 看不到它，于是实测里
一个真排了 123 秒的 worker 对 owner 说"我没有等待"。所以同一条老化时钟（`capacityWaits`）在候选被选中、
`delete` 之前被读一次，`waitedMs = now − 首次推迟时刻`，经 `StartWorkerInput`/`ResumeWorkerInput` 交到
`buildWorkerPrompt` 的 `capacityWaitedMs`，prompt 里出现一句
`本任务在容量队列里等了约 N 分钟（原因：机器容量已被占用）。`（不足一分钟说"约 N 秒"）。从未被容量推迟
过的派发**不含这句**。除 `waitingFor` 外不新增任何计时：这是同一份记账的第二个读者，不是第二只表。

## 七、`ResourceProbe`：Node-free 端口，v1 只做统一 API

```ts
export interface ResourceProbe {
  parallelism(): number                      // os.availableParallelism()（尊重 cgroup / 亲和性）
  memoryBudget?(): number | null             // 字节；可用内存的【下界】，或"平台不说"
  pressure(): number | null                  // 0..1 粗压力，或"平台不说"
  workerUsage?(pid: number): number | null   // 单个 worker 进程的占用，或"平台不说"
}
```

### 7.1 `null` 是一等公民

**"无信号" ≠ "空闲"**。`null` 绝不能被读成"资源充足"：

- `memoryBudget()` 在**下限门开启**时返回 `null` = "无法确认下限" → **推迟派发**，不是"内存够用"；
- `pressure()` 返回 `null` = "说不清"，任何调用方都不得当作 `0` 去放宽并发或调低 weight；
  v1 没有任何"按压力放宽"的逻辑，所以诚实的读法就是"不调整"；
- `workerUsage()` 返回 `null` = "这个进程的占用未知"，不是 `0`。

**可选成员缺席**与**实现但返回 `null`** 是两件事，刻意区分：

- 成员**缺席**（端口没实现这个信号，v1 未做平台适配器）→ 对应的门**不生效**，这是降级路径；
- 成员**实现但返回 `null`**（平台不肯说）→ 对应的门**保守**（内存下限门推迟）。

### 7.2 宿主实现（唯一允许有平台分支的 seam）

`createHostResourceProbe()` 只用**统一 Node API**：

- `os.availableParallelism()`（尊重 cgroup 配额与 CPU 亲和性；老运行时退回 `os.cpus().length`）；
- `os.freemem()`：**粗信号**，只作下限门，取 `min(freemem, cgroupLimit)` —— 是下界而不是精确值；
- `process.constrainedMemory()`：与 `os.totalmem()` **夹取**，并识别 `1.8e19` 这类**"无约束"哨兵**
  （cgroup `max` 被读成数字）。1.8e19 字节当预算是永远关不掉的闸门，必须当"无约束"处理；
- `pressure()` **恒为 `null`**：POSIX/Windows 适配器本任务不做。

实测（2026-10-02）：`os.totalmem/freemem` = 15.6/12.8 GB、`process.constrainedMemory()` = **1.8e19**
（哨兵）、cgroup `cpu.max` = `max 100000`（无 CPU 配额）。

### 7.3 空闲内存下限门

低于配置阈值（`minFreeMemoryBytes`，默认 **256 MiB**，`0` 关闭）时**推迟派发**（闸门，不是拒绝）。
256 MiB 是刻意低的：`freemem()` 是粗下界，阈值高了会把普通工作误停；低于它则进程有真实的 OOM 风险。
探针与容量都**可注入**（`HostOptions.probe` / `HostOptions.capacity`，引擎侧 `EngineOptions.probe` /
`EngineOptions.capacity`），所以两条门都能在测试里被确定性地打开、关闭与越界。

## 八、v2：平台适配器与实测校正（接口位置与降级路径）

本任务**只做 v1**：接口、统一 API、两条门、可观察性。v2 的落点已经留好，不需要改核心形状：

| v2 能力 | 接口位置 | 未实现时的降级 |
|---|---|---|
| CPU / 内存压力信号（POSIX `/proc/pressure`、Windows 计数器）| `ResourceProbe.pressure()` | 返回 `null` → 不调整（v1 现状）|
| 单个 worker 进程归属与占用 | `ResourceProbe.workerUsage(pid)` | 成员缺席 → 不按进程记账 |
| 按实测校正 weight（跑完之后回头修正申报）| 新字段（如 `NodeRecord.observedWeight`），仍可选带默认值，`DOMAIN_VERSION` 保持 1 | 只用申报值 |
| 按压力**放宽**并发的依据 | 只允许在 `pressure()` **非 null** 时使用；`null` 永不放宽 | 维持 capacity 硬闸门 |

平台分支**只允许存在于宿主侧这一处 seam**（`createHostResourceProbe`）；core 里出现任何
`node:` / `process.` 的硬件读法都是设计违规。

## 十、边界（本设计**不做**什么）

- 不做"按机器实际负载动态调 capacity"——capacity 是启动时派生一次的**静态上界**，v2 才谈校正。
- 不做平台适配器（`pressure` 恒 `null`）。
- 不按 weight 排序队列：FIFO + 老化是刻意的，否则重任务永远优先、轻任务被反复插队饿死。
- 不改 `hung`/`roundMs`（只针对 `running`）：排队中的节点天然不受影响。
- 不引入"受理失败"路径：容量永远不拒绝，只推迟。
